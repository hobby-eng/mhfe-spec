## Review evidence

### Scope and methodology

The requested scope was a maximally careful review of `SPECIFICATION-PLAIN.md` for correctness of information and technical details, scientific errors, and credibility of claims, reported in the format of the wallet-tools `FULL_AUDIT_GUIDE.md` and `AUDIT_STANDARD.md`. The review was read-only and adversarial: no statement was accepted on the basis of existing tests, the implementation's own vectors, earlier reports, or author assertions.

Methods used:

1. **Full read** of `SPECIFICATION-PLAIN.md` (all 2185 lines) with a checklist of every normative rule, formula, number, probability, table, and citation.
2. **Independent implementation.** A Python implementation of `MHFE-BIP39-256-EXPERIMENTAL-2` was written in a scratch area from the specification text only (BLAKE2b-256 salt derivation, Argon2id via `cryptography`, HMAC-SHA-256 masks, balanced Feistel forward and inverse, universal `E || Trunc_r(SHA256(E))` packing, BIP39 encode/decode with the official English wordlist, automatic source-length detection). It was run against all six `vectors/zero-*.json` files and compared every intermediate value. Script SHA-256 `f0232ff4e884328f1b9bf1a63e1f50b73734598ebbeea46c0db9cfeb6edea5fa`; wordlist SHA-256 `2f5eed53a4727b4bf8880d8f3f199efc90e58503646d9ff8eff3a2ed3b24dbda`.
3. **Numeric re-derivation** of every probability, percentile, expectation, memory volume, and time figure in the document.
4. **Primary-source citation checks** for all 36 references: GitHub API for pinned revisions, authors, and dates; raw source inspection of the cited community projects; RFC Editor, NIST CSRC, Unicode, arXiv, Springer, and IACR ePrint pages for academic and standards references; PDF text extraction for Patarin 2003 and Hoang–Rogaway 2010.
5. **Cross-file consistency** between the plain copy, `README.md`, `CHANGELOG.md`, `CITATION.cff`, `vectors/README.md`, and the license files.
6. **Implementation-claim checks** against the local `mhfe` working tree (source, tests, workflows, `Cargo.lock`, `measurements/*.json`) and against the reviewing host's hardware facts for the measurement table.

Exclusions: no cryptanalysis beyond re-deriving the document's own bounds; no WASM or browser execution; no rebuild of the Rust implementation; no review of the implementation's code quality (covered by the implementation repository's own audit and an earlier separate review). Author-side historical statements that leave no artifact ("reproduced twice byte-for-byte") could not be checked.

### Informational observations and recommendations

#### AUD-001-DOC002 — Info — Independent reproduction now covers both directions of all six vectors

§Test Vectors (lines 1970–1976) states that the six vectors' *forward* rounds were independently recalculated and that only the Rust generator completed the inverse round trip. This audit's separately written Python implementation reproduced both the forward and the inverse permutation, the automatic source-length detection, the recovery verifier, and the container mnemonics for all six files, and it rejected the `PIM = 1` container under `PIM = 0` with a verifier mismatch. The sentence is not wrong; it understates the available evidence. If the author wants to record it, the wording can say that a second independently written implementation reproduced every vector in both directions, while keeping the caveat that this is a scratch verifier, not a maintained interoperable implementation, and not a security review.

#### AUD-001-DOC003 — Info — Reference [17] is an attack paper cited among security results

§Patarin and beyond-birthday security (line 984) cites [14], [15], [17], [18] for the statement that balanced Feistel "can achieve security far beyond the basic birthday scale". [17] ("Generic Attacks on Feistel Schemes") presents distinguishers on 5 and 6 rounds with cost O(2^n) and O(2^{3n/2}) and recommends at least six rounds; it is an upper bound on achievable security, not a proof. The citation is defensible because the attack costs exceed the birthday scale, but the sentence reads as if all four references prove security. A one-clause qualification ("[17] gives the matching generic-attack costs") would make the attribution exact. §Luby-Rackoff and Patarin (line 1259) already describes [17] correctly.

#### AUD-001-DOC004 — Info — "Balanced Feistel wins when rounds are scarce" refers to Appendix E, Fig. 6

Lines 1804–1808 attribute to "the accompanying text" of Fig. 4 the statements that imbalance helps with enough rounds and that balanced Feistel wins when rounds are scarce. The paper's text reads: Fig. 4 shows that "given an adequate number of rounds, imbalance helps", and "the same point is illustrated differently in Appendix E, Fig. 6; when rounds are scarce, balanced-Feistel wins; but as rounds become more plentiful, imbalance becomes increasingly helpful". The quoted content is accurate; citing Appendix E, Fig. 6 for the "scarce rounds" clause would be more precise.

#### AUD-001-DOC005 — Info — Header block carries no document date

The header block (lines 5–15) gives `Version: 0.3.0` but no created or updated date, unlike the BIP-style header it imitates (`Assigned`/`Created`). `CITATION.cff` records `date-released: 2026-09-22` and `CHANGELOG.md` records `0.3.0 (2026-09-22)`. Adding the same date to the header would let a printed or copied specification be dated without consulting companion files. Citations inside the document use "[Accessed: Sep. 18–22, 2026]" dates that are consistent with this release date.

### Findings

#### AUD-007-SEC001 — Medium — Deniability theorem hypotheses omit independence from oracle tables

- **Category:** SEC; **status:** verified; **current release blocking:** false, because the stated
  correction checks pass.
- **Affected files:** `README.md`, `docs/DESIGN-NOTES.md`, `CHANGELOG.md`.
- **Reproduction:** Read the original experiments and theorem statements: uniform source entropy
  independent of passwords is required, but independence from the shared oracle tables is omitted.
  Consider a source sampler E = SHA-256(c) for a fixed public c in the random-oracle model, used in
  both games. E is marginally uniform and password-independent, yet the adversary can query c and
  test whether the disclosed opening equals E. This contradicts the stated small advantage bound
  under those incomplete hypotheses.
- **Expected behavior:** State the oracle-independence assumptions actually used by the coupling
  proof, consistently in both suites and in the README summary.
- **Observed behavior:** The original statement admitted an oracle-dependent source sampler that the
  proof did not handle. The corrected experiments require freshly uniform raw source entropy
  independent of the oracle tables, passwords and adversary prior information, and a fixed
  oracle-independent password distribution. Initial password draws are independent; the later
  rejection conditioning is distinguished. The assumption is about raw E, not the verifier-bearing
  packed X.
- **Impact:** A formal claim was stronger than its proof. This counterexample is not evidence of a
  practical attack on a wallet generated from independent cryptographic randomness. Suite algorithms
  and numerical bounds are unchanged.
- **Recommended fix:** Add these hypotheses to the experiments, theorem statements, suite-4
  adaptation, README summary and changelog.
- **Required verification:** An independent skeptic must check that the counterexample is excluded
  and that raw entropy is distinguished from the oracle-dependent packed state; rerun document and
  analysis checks.
- **Verification:** Confirmed by the skeptic and by the final source read; documents 15/15 and
  analysis 64/64 pass. The revised text was observed during concurrent edits; this report does not
  assign exclusive authorship.
- **Source/evidence hashes:** Exact original and final values and retained evidence names are in the
  JSON companion.

#### AUD-007-FUN001 — Medium — Owner-confirmed CLI re-encryption omits a reference for checking the replacement backup

- **Category:** FUN; **status:** verified; **current release blocking:** false, because the stated
  correction checks pass.
- **Affected files:** `../mhfe/src/bin/mhfe/rekey.rs`.
- **Reproduction:** Follow the CLI rekey branch for a recovery without an internal verifier,
  confirmed by displaying the phrase to its owner. In the initial file, seal followed owner
  confirmation without deriving and presenting a wallet reference for rehearsal of the replacement
  backup.
- **Expected behavior:** Before creating a replacement from an owner-confirmed unverified reading,
  derive a wallet fingerprint with the declared BIP39 passphrase, where applicable, and give it to
  the owner for rehearsal of the new container.
- **Observed behavior:** The implementation now obtains any declared nonempty passphrase, derives
  the fingerprint after owner confirmation and before seal, and includes it in the next-step
  rehearsal instructions. The displayed source status remains owner-confirmed; the derived
  fingerprint is not falsely described as independent evidence about the old backup. The explanatory
  prompt now also describes this use of the passphrase.
- **Impact:** The omission removed a prescribed safeguard against retaining an incorrect replacement
  backup. No incorrect mnemonic output or direct compromise was demonstrated.
- **Recommended fix:** Derive the rehearsal reference before encryption and include its purpose in
  the passphrase prompt and final instructions.
- **Required verification:** Trace confirmation, passphrase handling, fingerprint derivation and
  seal ordering; run existing rekey rule tests and the published BIP32 master fingerprint
  known-answer test.
- **Verification:** The source ordering and final instructions were independently reviewed; three
  rekey tests and one fingerprint test pass. Full-cost interactive owner-confirmed rekey was not
  run.
- **Source/evidence hashes:** Exact original and final values and retained evidence names are in the
  JSON companion.

#### AUD-007-UI001 — Low — Script-mode container repair omits the required per-word change record

### Assessment and limitations

All three confirmed findings are corrected and verified within the specified evidence scope. No
remaining confirmed specification/supplement contradiction, formula error or accidental bibliography
identity swap was found. New publication still requires release metadata and the separately scoped
release procedure.

- A specification audit and a focused CLI follow-up are not a whole-program release certification or
  a proof of concrete MHFE security.
- Full-cost Argon2 replay was deliberately not rerun. Recorded-key reconstruction independently
  checks salt/mask/Feistel/packing arithmetic, but cannot establish that the stored keys are fresh
  correct Argon2 outputs.
- The three suite-4 wrong-password/settings recovery outputs were not independently recomputed. The
  length-mismatch refusal and 67 pre-Argon2 cases were checked.
- No full-cost interactive owner-confirmed rekey session was run; its fix was verified by source
  ordering, focused CLI rule tests and fingerprint known answers.
- Browser runtime, OS isolation, Docker/reproducible builds, whole-program CI and remote release
  assets were not rerun. Signature blocks were inspected where available; cryptographic signature
  verification was not performed.
- Literature work was focused: not all 64 cited full texts were semantically checked. Some primary
  PDF fetches failed, including the OKVS primary PDF. Numerical proofs in every cited paper were not
  independently rederived.
- Python normalization probes used Unicode 16.0.0. They verify the public examples, not general
  Unicode 18 conformance.
- Some superseded specification and implementation hashes are unavailable locally; no replacement
  hash mapping is invented. Current corpus provenance can be established through available pins and
  byte comparisons.
- Concurrent authorized edits and an implementation commit occurred during the review. Initial and
  final source manifests are distinct and retained; final checks bind to final bytes, not only to a
  commit ID.
- The current published version is 0.5.0 and new changes are under Unreleased. Publication requires
  a new version/date and an implementation revision that includes the final changes; an audit does
  not authorize tagging or publishing.

Published version/date and the implementation pin must be set during the next release preparation;
this review does not authorize a commit, push, tag or publication. Suites 3 and 4 remain
experimental. The three findings do not establish that all other defects are absent.

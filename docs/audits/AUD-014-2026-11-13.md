# AUD-014 — Rust-to-Lean code-proof audit

## Assessment

No false checked theorem or concrete mismatch in the reviewed valid-input cipher, packing and
recovery computations was identified. This is a substantial, useful **conditional functional
correctness proof of a hybrid extracted/hand-translated model**. The actual source→Charon→Aeneas
chain was rerun without network; fresh generated Types and Funs are byte-identical to the proof's
inputs. All 28 active modules were freshly elaborated and independently replayed through Lean's
kernel. All 135 named proof theorems have exactly the advertised standard-axiom closures.

This does not establish that every production Rust function, a native/WASM executable or the
whole utility is formally verified. The semantic correspondence of the manual translations,
external dependency models and compiler pipeline remains trusted. Actual Argon2id, BIP39 text and
seed derivation, OS/memory effects and complete probabilistic security-game transfer are outside
the checked result. These boundaries are detailed below, not inferred away from a clean axiom log.

**Publication recommendation:** keep the proof, correct the regeneration status handling and
the concrete documentation findings, and publish with its exact assumptions and exclusions.
The Medium finding blocks treating the advertised regeneration procedure as a reliable
fail-closed verification gate. It does not negate the independently successful regeneration or
the validity of the current Lean terms. Low wording findings do not independently block release.
No production/proof/specification correction was applied, and no commit or push was made.

## What the checked theorems mean

The central chain is actual Rust source → a small signature-adjusted/opaque extraction harness →
Charon LLBC → Aeneas types and function bodies → exact splice with manual bodies → monadic
execution theorems → a byte specification → bit-vector Feistel and existing model ciphers.
Each arrow has a different assurance level; the kernel certifies only the Lean propositions
about the definitions presented to it.

The notation `f ⦃ r => P r ⦄` uses Aeneas total `WP.spec`/`DWP`: it excludes RustM panic/fail and
divergence. A returned Rust `Result::Err` or callback `Break` is still a normal returned value.
The base Feistel/Cipher theorems constrain a successful Continue result while allowing those
normal error/cancellation outcomes. They are not mere partial-correctness claims, nor do they
by themselves guarantee a container will be returned.

Success.lean adds real successful-return theorems. Under EngineComputes, EngineOk, continuing
callbacks and valid invariants, the round returns Ok, forward/inverse return the computed state,
and decryption of an admitted container returns a recovery. Encryption also requires that its
input is not a fixed point; the correct protocol behavior at a fixed point is refusal. An
abstract always-successful A engine can meet these premises, so these results are not globally
vacuous. An always-error engine is not a counterexample to them because it fails EngineOk.

EngineComputes is itself universal over engine states/inputs and demands return, allowing inner
Err and requiring the correct A key only on Ok. EngineOk is even stronger: every call on every
state/password/salt/memory/pass/key must succeed, including invalid or unreserved parameters.
The real native engine correctly rejects excessive memory requests and invalid parameters, so
it cannot satisfy this global contract. The Lean native placeholder always returns OutOfMemory.
Two fresh checked contract witnesses show that the placeholder satisfies EngineComputes for any
A and cannot satisfy EngineOk. Thus the generic success repair is real, but successful execution
of the native implementation has not been instantiated. A reachable-state/accepted-parameter
contract would be needed to prove that claim without demanding success on impossible requests.

Early suite/stated-length rejection and the suite4/24-word creation refusal need no engine
contract at all: they quantify over every engine, including one that diverges, because those
branches execute before engine work. This is stronger and should be credited separately.

WorkOk, SecretOk, PhraseOk and workspace geometry are explicit valid-input invariants. HostTotal
or CallbackTotal also requires callbacks to return. A summary saying no panic/always returns
from input validity alone must retain those dependency/callback conditions. Logical zero values
in into_state do not establish volatile physical erasure or absence of compiler/OS copies.

## Coverage and correspondence

The specialist annexes below contain requirement-by-requirement and source/theorem-line tables.
Their principal conclusions are:

- Exact domain strings, no added NUL, twelve forward0..11/inverse11..0 rounds, correct geometry
  in both suites, correct entropy-field placement, BE32 serialization and MEM-level versus KiB
  distinction were checked. All valid work-factor arithmetic bounds fit U32.
- The salt is the first16 BLAKE2b bytes and the mask the first half-length HMAC bytes. The
  32-byte key's explicit64-byte padded block is correct under RFC2104 and the pinned HMAC crate;
  its internals/security remain outside Lean. No padding discrepancy was found.
- Workspace slice partitions, inverse reassembly, equal-length XOR/swap, engine mutation/error
  propagation and callback FnMut state were traced through the handwritten/generated callers.
- Packing uses the exact SHA-prefix verifier, length detection preserves [12,15,18,21] order,
  the nontrivial length cascade respects guard precedence, and both reading lists/verification
  flags and suite/count admission agree with the dated specification.
- Creation checks the computed container differs from X and its inverse equals X. The real
  English-word codec self-check is assumed by the synthetic Phrase encoding/read_text model.
- WalletCheck proves digest/seed_passes and its two-zero-byte predicate. Full Seed::derive/
  passes wrappers, NFKD/PBKDF2, generation/retries and evaluation on every 24-word reading are
  not supplied as final code theorems.
- The roundtrip/original-reading facts are useful components. No single exported public-call
  Hoare theorem executes encrypt, decrypt and readings in sequence and concludes original
  membership. The same pure A contract across engine states/calls is required for composition.
- The byte/bit/model bridge is genuine pointwise functional equality for instantiated A/B/H
  tables and both suites, plus suite3 known-pair/finalize endpoints. It does not prove table
  sampling laws, full adversary/host observations, budget traces, domains, records or a transfer
  of all probabilistic security bounds to Rust. Conditional error selection also needs treatment
  before claiming equality of success-conditioned distributions.

The source-first reviews found no normal-path behavioral error in the five manual functions or
their active callback adapters. That is reviewed trusted correspondence, not a formal proof of
Rust semantics. All cryptographic and host-model exclusions are retained even when only Lean's
standard three logical axioms occur in the theorem closures.

### Interrupted and corrected audit attempts

The initial Cipher compilation was stopped by the audit's own overly sensitive resource guard,
which interpreted a few background swap-ins, with no swap-out or memory PSI pressure, as sustained
pressure. The parent records exit75 and the stopped inner scope exit -15 (SIGTERM). The guard was corrected
to require swap-out or swap-in with actual memory-pressure stalls; the 5% reserve and swap-free
audit scopes stayed in force. All 116 frozen inputs were rehashed before reusing earlier successful
module outputs. Cipher was rerun successfully, followed by the remaining modules. Its valid
record is **compile-resume-MhfeCore.Proofs.Cipher**, not the stopped compile-Cipher attempt.

The first new inventory driver failed parsing because the local variable `name` was reserved
under imported syntax. Only the audit driver's variable was renamed to `declaration`; proof sources
and axiom rejection criteria were unchanged. Initial source/command/log artifacts are retained,
and the corrected inventory and all controls pass. Initial version discovery also tried unsupported
--version flags for Charon/Aeneas; corrected documented forms `charon version`/`aeneas -version`
return0. These tooling attempts are not concealed or counted as mathematical failures. They do
not justify saying every recorded audit command exited0.

#### What the critical proof routes actually establish

##### Message serialization

`Proofs/Message.lean` follows the extracted iterator rather than assuming its final byte list.
`flatNext` and `flatState` describe the remaining option-array/inner iterator; both next-state
lemmas establish the actual flattened sequence. `write_message_loop_spec` tracks the write
offset, the BE32 sequence already written and the untouched suffix. `to_be_bytes_be32` connects
the library's actual bit-vector byte operation to four explicit big-endian bytes. The final
`write_message_spec` requires exactly enough buffer for those fields and the right half.

The accepted message fields are U32 values. The specification's `be32 Nat` is modulo2^32, but the
code's values already lie in U32 and valid MEM/PIM/ENT/i are much smaller. Thus modularization does
not conceal an overflow in the admitted protocol settings. The final proof also preserves the
complete right-half bytes, rather than only their length or checksum.

##### Workspace and one round

`Proofs/Workspace.lean:30` and line44 define exact message/workspace sizes; `WsInv` at line47 tracks geometry,
the secret's length and both logical halves. `workspace_new_spec` initializes the halves from
the input, and `parts_spec` proves the six mutable parts have the expected lengths and that their
backward functions restore the state. These invariants discharge the slicing and split-first-chunk
preconditions before those operations are used in the round proof.

`round_spec` at `Proofs/Feistel.lean:131` calls the actual code functions for message, salt, password
read, memory/pass arithmetic and engine, then the mask and swap. The left-masked branch proves
(R,L xor M(R)); the right-masked branch proves (R xor M(L),L). Equal lengths are established before
`xorZip` is identified with the specification's zipWith. Thus its shorter-input truncation does
not drop half bytes on the valid path. The engine may update its own state; the remaining
permutation settings stay fixed.

The workspace theorems prove logical values. `into_state_spec` at line237 gives the concatenated
halves, correct logical length and zeros in every remaining workspace byte. This does not prove
volatile stores, stack erasure, absence of compiler copies, mlock, dump exclusion or OS behavior;
those are modeled or explicitly external.

##### Twelve rounds, errors and callback outcomes

The forward-loop invariant at `Proofs/Feistel.lean:241` relates k completed rounds and remaining
fuel to the same initial state. The inverse-loop invariant at line305 accounts for the descending
round index and ascending callback counter. In each direction an Err or Break is returned
without claiming a final state; only Continue receives the full twelve-round postcondition.
The base state/length proofs are not accepted by assuming an already-correct final permutation.

`forward_spec:370` and `inverse_spec:403` are total-correctness statements in Aeneas's `WP.spec`,
with conditional **successful-state** conclusions. `Aeneas/Std/WP.lean:56` defines this via DWP;
lines103–106 reject RustM fail/divergence, so these are not merely partial-correctness triples.
However a normal Rust `Result::Err` is still a returned value and satisfies the guarded result
postcondition. `EngineComputes` itself requires every engine invocation to return; it permits Err
and only constrains key bytes when the invocation returns Ok.

The callbacks must be total under `CallbackTotal` at line234. The condition is actually for every
state and every i≤12, including i=0, although the loops only call1…12. It is stronger than strictly
necessary. The unproved public callback cancellation trace/stop-before-next-round property remains
separate; proving output correctness on Continue does not prove that whole observable trace.

##### Byte/bit bridge and the two security-model cipher definitions

`Spec/Bits.lean:18` extracts most-significant bytes first; `beNat:22` uses the first byte as most
significant, and `fromBytes:27` turns that number into an 8n-bit vector. `toBytes_xor:40` preserves
bytewise XOR. `toBytes_fromBytes:89` recovers every exactly-n-byte list; no signed conversion or
reversal is involved.

`Spec/Bridge.lean` proves round commutation and forward/backward list order, including arbitrary
round-count n. It explicitly requires every mask to have the right length. It is not simply an
alias equating two functions with identical names. `Spec/ModelLink.lean` then defines tables B, A
and H from the same byte primitives and settings. `modelMask_eq:51` uses both 16-byte salt and
32-byte key byte/bit round trips; `modelMasks_eq:59` aligns all Fin12 round masks. The cipher
equalities at lines78 and92 apply the independently proved byte-round bridge to the existing
`DeniabilityModel.cipher` and its inverse.

The suite3 specialization `perm_eq_knownPairCipher:111` has the fixed 128-bit halves. The inverse
endpoint `permInv_eq_finalize:121` uses the actual `CipherExecution.finalize_decrypt` theorem for
the oracle program, not a newly assumed inverse. The supplied G table is arbitrary because this
recovery computation does not use G. These are pointwise executions against instantiated tables,
not equalities of their probability laws or query-count distributions.

`Proofs/ModelCode.lean:24`, `:41` and `:59` compose those equalities with the real extracted/spliced
forward/inverse statements. They require EngineComputes, total callbacks, Matches and an input
equal to the bytes of two model halves. They conclude the returned Continue state's bytes, not
arbitrary error/callback observations. The input representation premise is meaningful for any
correctly sized input: apply `fromBytes` to each half and the proved byte round trip reconstructs
it. No separate exported wrapper eliminates that representation premise, but it is not an
uninhabited or algorithm-correctness premise.

#### Success hypotheses: useful new endpoint, real instantiation limit

##### The distinction already handled correctly

An engine which always returns Err can satisfy EngineComputes for any A. Consequently the
Continue-only conclusions alone cannot establish that code ever produces a container. The
artifact now has `Success.lean` with `round_ok:23`, `forward_ok:228`, `inverse_ok:255`,
`decrypt_ok:299` and `encrypt_ok:434`, using EngineOk and continuing callbacks. These results are
meaningful additional statements. Abstract engines that always return a supplied A key provide
models of those premises; there is no global contradiction or assumed final-cipher equality.

The non-fixed-point premise of encrypt_ok is also necessary. For some arbitrary primitive functions
the twelve-round permutation is the identity, in which case correct creation refuses every input.
The success theorem is not supposed to prove a container for such an input. The artifact makes
the fixed-point exclusion explicit.

##### Candidate correspondence/claim issue: EngineOk cannot hold for the native implementation

`Success.lean:20`–`:21` defines EngineOk universally over **every** engine state, password, salt,
memory, passes and initial key. It requires Ok even for invalid KDF parameters and for a requested
memory size beyond the engine's reservation. The native Rust implementation correctly refuses
those cases at `src/engine/native.rs:99`–`:103`.

A concrete source-level witness needs no heavy computation: reserve an engine for one valid work
factor, then ask it for more blocks than reserved. The branch at line99 returns OutOfMemory before
hashing. Or request passes0, which its Argon2 parameter construction legitimately refuses. Either
call is among EngineOk's universally quantified inputs even though the MHFE operation under review
never makes that call. Thus having sufficient resources for all **reachable valid** calls does not
establish EngineOk. The separate Lean native-engine placeholder is even more explicit:
`Assumptions/FunsExternal.lean:348`–`:357` always returns OutOfMemory and cannot instantiate this
success premise.

This does not falsify the conditional success results, and native/WASM engines are explicitly
outside the proof. It limits the documentation's statement that the former vacuity issue is
“fixed” for actual code. It is fixed at the generic abstract-contract level; it is not an
instantiated successful-execution theorem for the native engine. The README explains global
EngineComputes and excludes native engines, but should also make this stronger EngineOk restriction
plain. A useful refinement is a work-factor/reachable-state engine success contract, with a
separate favorable-resource assumption. No protocol parameter should be reduced to satisfy it.

This candidate was sent to the coordinator for challenge; severity should follow the publication
claim actually made. It is a model-coverage/documentation issue, not a claim that a correct native
engine needs to succeed on invalid requests or a runtime vulnerability requiring a trusted engine
to misbehave.

#### Functional correspondence versus probabilistic security transfer

The final proved relation is of this shape:

`successful code bytes = byte encoding of cipher(instantiated A,B,H)(state)`.

That is a real and useful functional link. The following stronger claims were **not found** in
the reviewed source or declaration searches:

- a theorem sampling the code primitives and proving their derived tables have the independent
  uniform laws used by the security games;
- an end-to-end correspondence between a Rust adversary/host interaction, its callback/errors,
  query-budget trace and a particular model game with the same win event;
- an instantiation of finite normalized-password domains or arbitrary passphrase transport for
  these code-byte endpoints;
- an implementation-level transfer of Theorem2's wallet-record experiment or its unobserved
  retry/failure convention;
- a proof that the bit-level SHA packing corresponds to the model's independently sampled G law;
  BIP39/PBKDF2 wallet composition remains external as disclosed;
- a native engine instance satisfying the success contract.

Searches followed the actual `ModelCode` endpoints, `Spec/ModelLink` and their imports; no
probability/PMF/game theorem is defined in those files. Their final conclusions are monadic
execution predicates with equal bytes. The imported security theorems retain their own hypotheses
and model restrictions. This cipher-component artifact does not prove an implementation
correspondence for either the earlier deniability record kernel or a later extension of it.

Simple model witnesses illustrate why the distinction matters without alleging an implementation
attack. Choose all opaque round masks to be zero: twelve swaps give the identity, so every source
is a fixed point and code correctly refuses creation. The functional bridge still holds; a
random-table fixed-point probability2^-W cannot be deduced for those fixed functions. Likewise a
total engine may return correct A bytes on Ok but selectively Err on some inputs, which
EngineComputes permits; distributions conditioned on successful code execution then need a
separate treatment. These witnesses challenge an unconditional transfer claim, not the
conditional results actually proved.

#### Manual and external trusted boundary

The critical Feistel operations are not all produced by an independently verified compiler.
`Assumptions/Translations.lean:51` implements workspace parts; line104 implements a round;
lines151/183 implement recursive forward/inverse loops; lines229/273 implement the two full

the meaning of Rust.

The list-based split-first-chunk, zip-XOR and swap helpers were also inspected. The zip retains
target suffix beyond the mask, matching Rust's zip; the proof establishes equal lengths before

`FunsExternal.lean` implements external iterators with lists and optional current-inner state;

`os.Pages.new` is modeled as always-returning zero bytes, stack overwrite as no value change, and

#### What the Hoare notation really establishes

The local pinned Aeneas library uses **total** weakest preconditions:
`Aeneas/Std/WP.lean:59-63` defines `spec` via `DWP`; `spec_fail` at 110,
`spec_div` at 113 and `spec_exists` at 153 show that panic/divergence do not
vacuously satisfy the triples. Partial `dspec` is a separate notion.

Consequently:

- `Cipher.encrypt_spec:389-401` and `decrypt_spec:150-162` establish that the
  modeled operation returns without RustM panic/divergence under its premises.
  Their *inner* result may be recoverable Rust `Err` or cancellation `Break`;

- This is stronger than a bare partial-correctness implication. However, it
  does not by itself assert inner successful completion.
- `Success.decrypt_ok:299-314` and `encrypt_ok:434-450` add an actual existential
  inner `Ok(Continue ...)` result. Therefore the old vacuity criticism has a
  substantive response, rather than merely a renamed conditional theorem.

##### Engine contracts

`Proofs/Feistel.lean:25-28` defines `EngineComputes inst A`: for every engine
state, password slice, 16-byte salt, memory/pass counts and prior key array,
the engine call terminates without RustM panic; if it returns inner Ok, its
key equals the fixed pure function A of the password/salt/memory/passes.
The state may change and inner Err is permitted. Requiring the same A over
all states also gives the consistency needed when the engine is reused for
inverse rounds or a later recovery.

`Proofs/Success.lean:20-21` defines `EngineOk`: every such call terminates and
returns inner Ok. Combined with EngineComputes, this means successful correct
tags rather than merely absence of panic. The proof explicitly combines the
two contracts in `round_ok:53-57` before taking the successful round branch.

The contracts are well-posed and satisfiable by an abstract engine that writes
any supplied A and returns Ok. They are not proved for production NativeArgon2.
In fact `Assumptions/FunsExternal.lean:346-358` intentionally models native
construction and native Argon2 calls as `Err OutOfMemory`. That model can
satisfy EngineComputes vacuously on inner successes, but it cannot satisfy
EngineOk, so no native successful-return corollary follows. The success
theorems do not magically verify the native engine by quantifying over E.

Both contracts quantify over all engine states and all memory/pass counts,
not only reachable calls of one accepted WorkFactor. This is stronger than
the production trait behavior: a real reserved native engine may legitimately
refuse a different memory size or invalid parameters. The artifact already
notes the overbroad EngineComputes domain; the same qualification matters for
EngineOk. A future useful production instantiation should use a reachable-state
and actual-call contract, or a fixed-work-factor engine invariant. No weakening
of correctness is needed; only the domain should match the implementation.

Argon2id version 0x13, four lanes, empty secret/AD and actual resource allocation
are not encoded by these contracts: `R/engine.rs:21-36` specifies them for the
Rust trait, while A remains any function in the proof. This is an explicit
assumed primitive boundary, not evidence that its implementation was checked.

##### Callback contracts and cancellation

`Cipher.HostCallbackTotal:17-19` requires every host callback call to terminate
with either decision. `Success.HostContinues:280-282` requires Continue on
every argument/state; `CallbackContinues:125-129` is the corresponding
round-callback contract. Callback state changes are retained by the generated
closure calls and the repaired FnMut wrappers.

The positive success endpoints thus exclude cancellation deliberately.
`R/cipher.rs:83-117` calls progress callbacks before each of the 24 creation
rounds and the unchecked-container callback between forward and inverse work;
`decrypt:152-155` supplies round/12. The relevant wrappers preserve those
arguments in the translated body. The proof establishes callback termination
or continuation as a premise, rather than deriving those properties for a
particular host implementation.

No final event/count theorem specifies all callback invocations, their exact
order, the absence of later engine calls after Break, or withdrawal of a
container already delivered to `on_unchecked`. The artifact expressly keeps
that cancellation/publication workflow outside scope. In particular NEW-5/6
cannot be credited merely because the function eventually returns Break:
the host may already have observed a provisional container.

#### HMAC padding: no discrepancy found

The primary reference is [RFC 2104, section 2](https://www.rfc-editor.org/rfc/rfc2104.html#section-2).
It hashes keys only when their length exceeds the hash block size, then pads the
effective key with zeros to that size. Therefore, for SHA-256's 64-byte block and
a 32-byte key `K`, both `K` and `K || zero[32]` normalize to the same block.
The latter has length exactly 64 and is not hashed as an overlong key.
This establishes `HMAC-SHA256(K, m) = HMAC-SHA256(K || zero[32], m)` for every
32-byte `K` and message `m`, conditional on the standard HMAC interpretation of
the external primitive.

The actual pinned implementation agrees with this interpretation:

- `mhfe_core/Cargo.lock:159` pins `hmac` 0.13.0; `:292` pins `sha2` 0.11.1.
- `src/feistel.rs:263`–`:274` copies the 32-byte key into a zero-initialized
  64-byte block, calls `KeyInit::new`, then updates with `DS_MASK` and `message`
  in that order and takes the leading output bytes.
- In the local Cargo source `hmac-0.13.0/src/block_api.rs:34`–`:39`, the HMAC
  key/block size is the underlying hash's block size. `KeyInit::new` at
  `:48`–`:49` calls `new_from_slice`; the latter at `:53`–`:63` obtains the
  derived key block and applies the inner and outer pads.
- `hmac-0.13.0/src/utils.rs:9`–`:18` initializes a zero block and copies the key
  unchanged when `key.len() <= block.len()`; only the other branch hashes it.
- `sha2-0.11.1/src/lib.rs:34`–`:36` selects `Sha256VarCore` with a 32-byte output;
  `src/block_api.rs:28`–`:29` gives that core a 64-byte block.

These dependency paths are under
`workingspace/cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`.

The Lean definitions do not substitute an unrelated HMAC convention:
`Proofs/Round.lean:23`–`:41` proves that the actual round-mask code invokes the
opaque HMAC on `key.val ++ zero[32]` and the correct concatenated message.
`Proofs/Feistel.lean:33`–`:35` defines arbitrary-key `hmacOfKey` by hashing only
keys longer than 64 and padding the resulting key to 64. Its only round use is
the fixed 32-byte Argon output. No overlong-key corner case is needed for this
application. The dependency source and RFC check remove the proposed padding
mismatch; they do not prove the opaque cryptographic primitive or its security.

#### EngineOk: coverage qualification, not a false-theorem finding

`Proofs/Success.lean:20`–`:21` quantifies `EngineOk` over every engine state,
password, salt, memory amount, pass count, and incoming key. The real native
engine can correctly refuse an amount exceeding its allocated work area
(`src/engine/native.rs:97`–`:102`), so it cannot satisfy this unrestricted
contract. Invalid parameter tuples also need not succeed. Consequently the
current success theorems are not an instantiation proving successful execution
of the concrete native engine, even for an individual valid configuration.

This does not falsify those conditional theorems. An abstract always-successful
engine can satisfy the premise; the proof artifact's native placeholder returns
`Err OutOfMemory` (`Assumptions/FunsExternal.lean:348`–`:357`) and is explicitly
outside the proof. `PROOF-README.md:61`–`:63` states the stronger success
premises; `:110`–`:112` explicitly excludes native and WebAssembly engines.
Classify the global-contract restriction as a scope/instantiation observation,
not a new Medium logical defect or evidence of an incorrect checked theorem.

Recommended final phrasing: no false checked theorem was identified in the
reviewed bridge; functional correctness is conditional on the stated external
models and engine/callback contracts, and successful execution of the real
native/WASM engines has not been proved by these theorems. This is not a claim
that kernel acceptance alone validates the manual Rust translation, external
models, or probabilistic security transfer.

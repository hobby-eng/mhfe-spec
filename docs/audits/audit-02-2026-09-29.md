## What the specification gets right

The normative README is implementable without guessing the cryptographic byte layout. It defines the suite/domain strings, raw bytes and bit order, BLAKE2b configured for a 32-byte digest (not a truncated 64-byte digest), BE32 memory/PIM/round bindings, twelve 128+128 Feistel rounds, inverse ordering, Argon2 version/lanes/secret/AD/output, HMAC mask, packing and BIP39 checksums. Integer resource formulas fit their stated ranges. The Unicode version is pinned, including rejection of unassigned characters, and plaintext word parsing is separate from password normalization.

The current draft already explains the limits that would otherwise be serious overclaims: no AEAD; no internal verifier for a 24-word original; probabilistic short-source detection; manual override and ambiguous readings; deterministic equality leakage; suite/settings recovery context; no proved honey-encryption distribution or plausible deniability. It explicitly calls the twelve-call and eleven-call claims conjectural and withdraws a lower bound that counted only Argon2 evaluations while treating all hashes as free. These are good corrections and should be preserved.

Source-length packing is correctly accounted for: 12/15/18/21-word sources have 128/96/64/32 verifier bits, respectively. The BIP39 source checksum is already the beginning of that same SHA256 prefix; it must not be added a second time to the security budget. The visible ciphertext checksum adds no wrong-password rejection. A 12-word source retains 128 bits of entropy despite its 256-bit packed representation.

## Detailed findings

### AUD-002-SEC001 — Intermediate round salts are described as public although their disclosure enables a one-call password filter

**Medium · open · release-blocking recommendation: True.** Affected: [README.md#L385-L390](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/README.md#L385-L390), [docs/DESIGN-NOTES.md#L654-L660](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/docs/DESIGN-NOTES.md#L654-L660), [docs/DESIGN-NOTES.md#L115-L123](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/docs/DESIGN-NOTES.md#L115-L123).

**Reproduction:** Take the public zero-12 fixture. Give the attacker the container and additionally S_10 from its transcript. For each password candidate compute S_11 from the container left half, perform one real default-cost Argon2id evaluation with OpenSSL, reconstruct L_11, and compare the derived S_10 with the leaked value. Test the correct and one wrong password.

**Expected:** Distinguish a salt that does not have to be an independently stored secret from intermediate state-derived salt values that the ciphertext-only cost argument assumes are unavailable.

**Observed:** The README says salt derivation uses public data; the supplement calls state-derived salts not secret without limiting the statement to exposed endpoints. The actual extra-leak experiment accepted the correct password and rejected the wrong password using one Argon2id call each (6.72 and 6.86 seconds).

**Impact and limits:** This is an inaccurate information-flow description with a concrete consequence for logging and diagnostics. It is NOT a ciphertext-only break: the experiment deliberately provides an extra intermediate salt. No production path leaking such a salt was discovered. The published-vector transcript is safe because its inputs are public. The cost claim needs its no-intermediate-leak premise stated explicitly.

**Recommended fix:** State that the inverse endpoint salt S_11 is public from the container, S_0 is known when the original is known, and intermediate salts, masks, keys and states are transient sensitive values. Forbid their production logging/export and make the erasure recommendation explicitly include them. Distinguish this from the absence of a stored secret salt.

**Verification after fix:** Review all ordinary-operation tracing and diagnostic paths; retain a public-fixture regression demonstrating the one-call filter and check that production interfaces expose no intermediate values. Correct both README and supplement. No suite/byte-format change is needed.

**Evidence:** `probe-leaked-salt.py`, `leaked-salt.log`

### AUD-002-FUN001 — Interactive CLI releases an unverified container into redirected stdout

**Medium · open · release-blocking recommendation: True.** Affected: [README.md#L254-L264](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/README.md#L254-L264), [src/bin/mhfe/encrypt.rs#L78-L111](https://github.com/hobby-eng/mhfe/blob/1dfbb7151712dac4baf37abe3459eedd681753e6/src/bin/mhfe/encrypt.rs#L78-L111), [src/bin/mhfe/terminal.rs#L180-L193](https://github.com/hobby-eng/mhfe/blob/1dfbb7151712dac4baf37abe3459eedd681753e6/src/bin/mhfe/terminal.rs#L180-L193).

**Reproduction:** Run the exact native CI binary with stdin attached to a PTY and stdout to a pipe, without --stdin. Enter the public zero-12 source and password twice. Read the pipe and stop the child as soon as the expected container is emitted.

**Expected:** A result passed to another program MUST NOT be released before reverse verification passes; eligibility for a human preview must depend on the output destination.

**Observed:** The expected container reached piped stdout after 73.74 seconds, before the Verified message and before reverse verification completed. The implementation selects the early-output branch solely from input.is_script(), while print_phrase writes stdout in both branches. The probe terminated the operation after observing the premature output.

**Impact and limits:** A downstream program or redirected file can receive and act on a result whose verification later fails or never finishes. No corrupted fixture or actual loss was induced. This is a new implementation finding uncovered by normative conformance tracing, separate from the earlier incorrect rehearsal message.

**Recommended fix:** Gate early presentation on a human output destination, or send only a clearly labelled preview to a terminal and reserve stdout for verified results. Handle stdin and stdout modes independently. Do not assume absence of --stdin means stdout belongs to a person.

**Verification after fix:** Use a PTY/pipe matrix: terminal-to-terminal, terminal-to-pipe, script-to-terminal and script-to-pipe. Inject verification failure and cancellation after encryption; machine-facing stdout must contain no container unless verification succeeded.

**Evidence:** `probe-redirected-output.py`, `redirected-output.log`, `redirected-output.stdout`, `redirected-output.tty`

### AUD-002-API001 — CLI line-based password transport cannot represent the full normative password domain

**Medium · open · release-blocking recommendation: True.** Affected: [README.md#L185-L194](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/README.md#L185-L194), [src/bin/mhfe/terminal.rs#L135-L178](https://github.com/hobby-eng/mhfe/blob/1dfbb7151712dac4baf37abe3459eedd681753e6/src/bin/mhfe/terminal.rs#L135-L178), [src/bin/mhfe/encrypt.rs#L211-L244](https://github.com/hobby-eng/mhfe/blob/1dfbb7151712dac4baf37abe3459eedd681753e6/src/bin/mhfe/encrypt.rs#L211-L244).

**Reproduction:** Pass alpha\nbeta and alpha\r as UTF-8 bytes to production WASM. Capture the normalized bytes at the engine boundary while deliberately stopping before Argon2. Supply the same intended newline-containing password twice to native encrypt --stdin using its documented line protocol.

**Expected:** Recovery MUST accept every password allowed by the fixed Unicode-17/NFKD/1..1024-byte rules. A recovery interface needs a lossless way to supply that domain, even if its convenient interactive field supports a subset.

**Observed:** WASM accepts LF, trailing CR, NUL and surrounding spaces and preserves their bytes. The repeated intended LF password is split into separate CLI answers and fails with exit 2 (passwords differ). read_line cannot embed LF in a field; strip_line_ending also removes a final CR before LF. The hidden terminal input is likewise line-oriented. There is no documented alternative password-byte transport in the CLI.

**Impact and limits:** A valid container made through a byte-capable integration can be unrecoverable through the CLI interface even though the underlying Rust and WASM cryptographic password implementation is correct. This is an input-transport/interoperability gap, not a defect in NFKD or the permutation. The conformance-class ambiguity should also be clarified in the specification.

**Recommended fix:** Add a lossless secret-input channel, for example a length-delimited stream, dedicated descriptor or explicitly encoded input format. Avoid secret command-line arguments. Document delimiter handling. Do not silently narrow suite-3 passwords: rejecting previously valid characters changes the frozen password definition and does not recover existing containers.

**Verification after fix:** Cross-interface recovery for LF, CR, CRLF, NUL, tabs, leading/trailing spaces and normalization-equivalent inputs; verify byte preservation. The present test confirms normalization and transport failure, not a new full-cost container for every control character.

**Evidence:** `probe-password-domain.mjs`, `password-domain.log`, `cli-newline.json`

### AUD-002-DOC001 — README overstates what equal containers imply

**Low · open · release-blocking recommendation: False.** Affected: [README.md#L485-L487](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/README.md#L485-L487), [docs/DESIGN-NOTES.md#L1038-L1061](https://github.com/hobby-eng/mhfe-spec/blob/4b41a74e5de8f1d24d4018d31cc0fe50c0997334/docs/DESIGN-NOTES.md#L1038-L1061).

**Reproduction:** Compare the unconditional equality statement in the README with the fixed-permutation qualifications in the supplement. Also consider two allowed source-length interpretations of one packed state.

**Expected:** Equality implies equality of packed state only when suite, normalized password, PIM and MEM identify the same permutation; equality of packed state is not always equality of source-length interpretation.

**Observed:** The README states that identical containers reveal the same phrase without those qualifications. The supplement correctly limits the converse to a fixed permutation and notes source-length ambiguity.

**Impact and limits:** This is a precision and consistency defect, not a ciphertext collision attack. Across different passwords/settings, the same container generally decrypts to different states; one packed state can also have both a short-source and a 24-word interpretation.

**Recommended fix:** Say that repeated encryption of the same packed source under the same normalized password, suite and settings is linkable. State the converse only for that same permutation and distinguish packed-state equality from source-length identity.

**Verification after fix:** Check the statement against the permutation definition and the deliberate ambiguous-source fixture; keep README and supplement wording consistent.

**Evidence:** Normative README versus supplement; mathematical counterargument, no production exploit claimed.

## Why one leaked intermediate salt matters

Let the attacker know the container `Y = L_12 || R_12`, settings, and additionally the actual `S_10`. For one guessed password:

```text
1. S_11 = Salt(11, L_12)                 # available from container
2. K_11 = Argon2id(guess, S_11)           # one expensive call
3. M_11 = Mask(K_11, 11, L_12)
4. L_11 = R_12 XOR M_11
5. S_10_candidate = Salt(10, L_11)
6. Compare S_10_candidate with leaked S_10.
```

The correct password necessarily passes. Under an idealized independent mask/hash model there are two accidental-match routes: the recovered 128-bit half can coincide, or a different half can collide in the 128-bit salt hash. Their combined probability is on the order of 2^-128 (approximately 2^-127 in that simplified model), not an independently proved exact bound for the concrete construction. The two experimental candidates demonstrate the filter, not its complete probability distribution. No original mnemonic or known plaintext is needed, but the extra intermediate salt is essential. Exposing every round salt therefore changes the threat model radically, even though ordinary password-hashing salts are normally public. The core conjecture explicitly relies on hidden intermediate states; the prose should not invite implementations to destroy that premise.

## Recommendations that do not change suite-3 bytes

### R01 — Separate conformance classes and strengthen final-output semantics

Define Core, CLI, Browser Client and Complete Application obligations. A core function cannot show a suite, ask twice or render warnings. Let an internal primitive return a typed UnverifiedContainer, but require a final container-export operation to complete reverse verification. Clarify how the SHOULD for verification interacts with the MUST NOT for machine output and the preview exception. This removes an ambiguity without changing ciphertext.

### R02 — Use explicit verification result types

Distinguish unchecked output, reverse_checked, short_verifier_match(words, bits), wallet_fingerprint_match and wallet_address_match. A generic verified=true is too easy to interpret as ownership or passphrase verification. Include the address derivation scope and say not_found_in_scope when a bounded search fails; a missing path match does not establish a wrong MHFE password.

### R03 — Publish a canonical suite-3 conformance corpus before stable release

Publish the 17 positive transcripts, negative vectors and Unicode boundary cases in mhfe-spec with immutable hashes and schema. Add LF/CR/CRLF, private-use and noncharacters; raw numerical API coercions belong in adapter tests. Keep production-cost known-answer tests separate from toy/reduced tests. Obtain another-author implementation: a second code path using independent OpenSSL is valuable but is not independent expert review.

### R04 — Keep performance claims conditional and add measured attacker scenarios

The arithmetic for 58 million years, 39 years and about 20.5 equivalent cost bits is consistent with the assumed 1 MHFE guess/s and 1.5 million PBKDF2 guesses/s. The rates are not benchmark results. Logical block accesses are not automatically DRAM traffic, and capacity, bandwidth and area-time models cannot be interchanged. Add exact hardware, optimized code, batching, password/salt reuse, memory-time trade-offs and sensitivity ranges; distinguish PBKDF2-only from complete address checking. Do not present the tables as a measured lower bound.

### R05 — Explain the parameter optimization objective explicitly

RFC 9106 recommends Argon2id t=1 at 2 GiB and notes t=1 is best for fixed defender time under its attacker model. Twelve passes are a valid project choice with a 2-GiB browser/memory ceiling, not the RFC preset and not established as globally optimal. Compare candidate memory/pass budgets empirically before a future suite. Do not reduce current suite-3 rounds or passes in place.

### R06 — Promote cumulative false-positive and reference-leak guidance to the short spec

For a selected 21-word verifier the per-uniform-candidate rate is 2^-32, but after q independent trials the chance of any false match is 1-(1-2^-32)^q. At one million trials this is about 0.0233%; at 2^32 trials about 63.2%. Auto detection is also dominated by the 21-word relation even for an intended 12-word source. Recommend selecting the known length during recovery assistance and confirming a wallet reference. These facts are mostly already in the supplement; promotion avoids overstating the word confirms. A no-passphrase master fingerprint can separately identify a mnemonic and remove the claimed pair-search advantage; document exactly what any saved reference derives from.

### R07 — Preserve recovery context as a portable offline package

State suite, supported implementation version, settings, wordlist, password encoding and reference path/network separately from the decoy plate, with an offline compatible release. Preserve access to suite-2 software. The current README reference link points to the repository root while suite3 exists on a WIP branch: pin the actual revision until release. No automatic suite guessing is safe for a 24-word source.

### R08 — Make historical suite-2 analysis unmistakably archival

Part II contains old PIM ranges and formulas lacking MEM alongside uppercase requirements, despite being non-normative. Replace the blanket read suite2 as current suite instruction with a precise applicability table or label every copied formula suite2. The current README is sufficient to implement suite3; the danger is copying the wrong historical formula.

### R09 — Keep entropy, passwords and recovery availability separate

The 256-bit state does not turn a 12-word source into 256 bits of entropy. Work factors do not repair correlated/reused passwords. The maximum joint MEM/PIM range is headroom: extrapolating the document own time model to 3 TiB and PIM1023 gives roughly 3-6 years per inversion, not a practical recommended profile. Publish realistic supported profiles and explicit resource/time ceilings without changing parameter mapping.

### R10 — Treat exact input matching and abort semantics as explicit adapter contracts

Specify raw versus normalized confirmation comparison (current CLI and client compare raw input bytes), ASCII word case handling, accepted whitespace, lossless binary/string transport and cancellation state. On cancellation after a preview, keep status unverified. Clarify that no copy/store during rehearsal prohibits external disclosure and persistence, not the transient internal representation required to derive a wallet.

## Numeric and theoretical review

Recomputed values: four independent draws from 7,776 words contain about 51.699 bits; five contain about 64.624 bits. At the assumed one MHFE candidate/s, half-space search for four words is about 57.93 million years. At 1.5 million PBKDF2 candidates/s it is about 38.62 years; the assumed speed ratio is 20.5165 cost bits. Two independent 30-bit secrets in the specified sequential pair-search model give about 12,195 years. These match the rounded headline values. Minor table rounding, such as about 54 versus 56 million botnet years for five words, is not a material cryptographic error.

The exact expected sequential costs, for finite uniform spaces and a fixed enumeration order, can be written more precisely as `(N1+1)*C1/2 + (N1*N2+1)*C2/2` without a mnemonic verifier, and `(N1+1)*C1/2 + (N1-1)*N2*C2/(2^(r+1)) + (N2+1)*C2/2` with independent false acceptance 2^-r. Dropping lower-order terms gives the document formulas. These are strategy estimates, not optimality theorems. A separate mnemonic verifier, reused secrets, nonuniform guesses or different search scheduling changes the problem.

For uniformly random candidate X, the selected-length acceptance fraction 2^-r follows exactly by counting possible E, without assuming SHA256 is random. Applying that fraction to wrong-password outputs requires the candidate-distribution hypothesis. The union bound for automatic detection lies between 2^-32 and 2^-32 + 2^-64 + 2^-96 + 2^-128; independence between length checks is not needed for that bound. Conditional ambiguity rates for correctly packed sources are heuristic, not the same counting result.

The one-skipped-round known-pair filter is a real structural observation: compute from both ends and compare the mask-free half relation across the missing round. The text correctly avoids proving eleven calls optimal. Twelve ideal Feistel rounds and domain separation do not, by themselves, establish the joint random-function assumptions for a password-indexed Argon2 construction. Investigating A1, low-entropy password distributions, multiple related samples and time-memory trade-offs remains worthwhile; none of these open questions is presented here as a discovered break.

## Primary standards checked

- [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html), sections 3, 4 and 7: Argon2 inputs, recommended parameters and the fixed-defender-time qualification. The first 2-GiB recommendation uses one pass; the draft already distinguishes its chosen twelve passes.
- [UAX #15 revision 57 / Unicode 17](https://www.unicode.org/reports/tr15/tr15-57.html), section 12: stabilized normalization rejects General_Category=Unassigned. Private-use characters are not excluded merely for being private-use. The revision pin is meaningful.
- [UAX #15 revision 58 / Unicode 18](https://www.unicode.org/reports/tr15/tr15-58.html): the cited document exists with the stated version/date; no fabricated-reference finding was made.
- [SLIP-0039](https://github.com/satoshilabs/slips/blob/master/slip-0039.md), encryption: four Feistel rounds, a PBKDF2 salt that includes R, optional identifier-derived prefix. The resemblance is real, not a proof for MHFE.

Only these selected external sources were freshly checked. This review does not revalidate every paper, novelty claim or bibliographic detail in the 44-item reference list.

## Recommended text changes

**Intermediate salts:** “The salt of the last round is derivable from the container, and the first-round salt is derivable when the original is known. Intermediate round salts are not public outputs. They, together with intermediate states, masks and keys, MUST NOT be logged or exported during ordinary operation. The ciphertext-only cost discussion assumes that these values have not leaked.”

**Input transport:** “Every implementation claiming recovery support MUST provide at least one lossless transport for all passwords accepted by this suite. A line-oriented convenience input MAY support a smaller directly typeable subset, provided the complete transport is documented. Input delimiters MUST NOT be treated as password bytes or silently remove password bytes.”

**Final output:** “A container exported as the completed result of creation MUST have passed reverse verification from its encoded words. Before that point it MAY be exposed only through an explicitly unverified human-preview channel. Whether stdout is machine-facing is determined independently of whether input is interactive.”

**Rehearsal:** “A built-in verifier match establishes consistency of a candidate at the selected source length. It does not establish wallet identity or validate a BIP39 passphrase. Applications MUST identify which kind of check succeeded and MUST NOT describe a built-in-only match as a wallet-reference match.”

**Equality:** “Under the same suite, normalized password, PIM and MEM, equal containers imply equal packed states. This implication does not extend across different permutations; packed-state equality may still permit more than one source-length interpretation.”

These are proposed editorial/application-contract changes, not applied patches. The final-output MUST strengthens the current universal SHOULD; it leaves the existing ciphertext definition intact. Changing password normalization, dropping currently valid characters, changing memory/pass mapping or the permutation itself would require a new suite under the draft own compatibility rule.

## Release assessment and limitations

The specification is substantially usable as an experimental byte-level definition; no need to redesign the Feistel/packing format was established. It is not a proven security standard. Correct the intermediate-salt description, qualify equality, publish the canonical suite-3 vectors and tighten conformance/result semantics. For the implementation, fix redirected output and lossless password transport, as well as the inherited parameter-boundary, rehearsal-message and erasure defects, before claiming full compliance.

- No real-browser GUI/CSP/lifecycle testing, second clean build or other-OS execution in this follow-up.
- No complete Unicode-17 normalization corpus or exhaustive protocol input domain. Fourteen accepted fixtures checked at the production WASM KDF boundary; invalid cases stop before it.
- Fresh structural replay uses recorded Argon2 outputs and does not independently validate them. Two real full-cost OpenSSL evaluations were added only for the leaked-intermediate-salt experiment. Prior full-cost native/C-WASM/two-positive-vector evidence is inherited and explicitly identified.
- No production intermediate-salt disclosure found. One-call filter assumes S_10 supplied as additional information; no claim of a one-call ciphertext-only attack.
- Exact model/effort unknown. AUD-002 is locally assigned in the specification repository sequence and not reserved upstream; same textual IDs in mhfe repository denote different records.
- No repairs, releases, pushes or remote mutations performed.

All four new records remain open. No fix commit or verification commit exists for this review. Recommendations have not been silently converted into failed MUST requirements. The unopened real-browser/platform work prevents complete application acceptance, even where core outputs and source formulas match.
